# Админка BizBox в Telegram

## Ежедневная работа владельца

Администратор: Telegram ID **6575928505**. Все заявки приходят в личный чат с **@Biznowbox_bot** — тем же ботом, из которого открывается приложение.

1. Клиент выбирает тариф, оплачивает через Kaspi и нажимает **«Я оплатил»** в приложении.
2. Бот присылает владельцу заявку: клиент, Telegram ID, тариф, сумма, статус чека.
3. Клиент нажимает **«Отправить чек боту»** и отправляет фото или PDF. Файл привязывается к его единственной ожидающей заявке; в карточке появляется **«Показать чек»**.
4. Владелец проверяет фактическое поступление денег в Kaspi. **«Подтвердить»** включает тариф, **«Отклонить»** оставляет прежний доступ.
5. Бот сообщает клиенту решение. Открытое приложение получает новый статус примерно за 20 секунд; при повторном открытии запрашивает его сразу. Есть ручное обновление статуса.

**/admin** показывает ожидающие заявки, первые пять за один вызов. После их обработки вызови команду снова. Это также способ восстановить карточки, если уведомление потерялось. Команды /start, /help и /status доступны клиентам; /admin — только владельцу.

Повторное подтверждение, повторный webhook или нажатие на старую карточку **не добавляют срок второй раз**. Решение фиксируется в одной транзакции. Изменить уже принятое решение кнопками нельзя.

## Сроки и заявки

- BUSINESS: **4 990 ₸**, PRO: **14 990 ₸**, срок — **30 дней**.
- Продление того же серверного тарифа добавляет 30 дней к более позднему моменту: сейчас или текущий срок окончания.
- Смена тарифа запускает новый период от подтверждения. Перенос остатка дней между тарифами не автоматизирован.
- У клиента может быть только одна ожидающая заявка. Повторное «Я оплатил» возвращает её. Для смены выбранного тарифа владелец сначала отклоняет старую заявку.
- Не более пяти новых заявок на аккаунт за 24 часа. Фото/PDF чека — до 20 МБ, загрузка прямо через Telegram; приложение не хранит бинарные файлы.
- Если клиент не запускал бота или заблокировал его, личное сообщение может не доставиться. Решение всё равно видно в приложении; повторная оплата не нужна.
- Уведомления используют сохранённый статус доставки и короткую блокировку отправки. Telegram не гарантирует ровно одну доставку при сетевом таймауте; редкое повторное сообщение не создаёт повторную подписку. /admin восстанавливает доступ к заявкам без фоновой очереди.

Кнопка «Я оплатил», наличие чека и подтверждение владельца — разные состояния. Банковское API и автоматическая проверка платежей не подключены. Отклонение заявки не делает возврат через Kaspi.

## Устройство серверной части

- Основной адрес API: `https://biz-box-v3.vercel.app/api/bizbox` — Vercel Node Function.
- Клиент передаёт исходный Telegram `initData` в POST body. Сервер проверяет HMAC с токеном бота, время выдачи, формат и ID. Подставленный `initDataUnsafe` не даёт серверных прав.
- Webhook: `/api/bizbox?action=telegram`. Проверяется `X-Telegram-Bot-Api-Secret-Token`; решение разрешено только ID владельца в его личном чате.
- Хранилище — отдельные таблицы `public.bizbox_payment_requests` и `public.bizbox_subscriptions` существующего Supabase проекта `wudelvuaasblxmogkixu`. Остальные таблицы проекта не меняются.
- Браузерные роли лишены прав на таблицы и RPC. RLS включён без публичных policies намеренно; INFO от Supabase Advisor об отсутствии policies ожидаем: доступ только серверный.
- Supabase Edge Function `bizbox-billing-store` сверяет хеш отдельного секрета, затем вызывает RPC от серверной роли. Полный ключ Supabase не передаётся браузеру или Vercel.
- Решения, подписки и привязка чеков сохраняются в БД. Бизнес-данные клиента по-прежнему сохраняются в Telegram CloudStorage.
- На зеркальном сайте `biz-boxv3.vercel.app` фронтенд обращается к основному API. CORS разрешает только эти два production адреса.

Старые подписанные коды остаются резервным способом. Серверная подписка хранится отдельно от кода; сохранение рабочего пространства не стирает одобрение администратора. Серверный статус не берётся из локального хранилища как доверенный. Клиентские модули остаются локальным интерфейсом; будущие серверные бизнес-API должны отдельно проверять права.

## Настройка и обслуживание

Vercel project: `biz-box-v3`, Production only:

```text
BIZBOX_BOT_TOKEN           токен именно @Biznowbox_bot
BIZBOX_STORAGE_URL         адрес Supabase Edge Function
BIZBOX_STORAGE_TOKEN       случайный межсерверный секрет
BIZBOX_WEBHOOK_SECRET      случайный секрет webhook
BIZBOX_SETUP_SECRET        секрет первоначального подключения
```

Все значения, кроме URL, хранятся как Secret, без префикса VITE_. Токен бота не читается из публичного кода. При изменении Vercel-переменных нужен новый deployment.

Первоначальная настройка: защищённый POST `{action:"setup",operation:"inspect"}` с `Authorization: Bearer <BIZBOX_SETUP_SECRET>` проверяет бота, хранилище и webhook. `operation:"install"` включает webhook, меню приложения и уведомляет владельца. Если у бота уже другой webhook, установка возвращает ошибку и не заменяет его. Не выполняй установку на Preview.

Локальная резервная конфигурация межсерверных секретов — `.secrets/billing-config.json`, не в Git. Для ротации storage token обнови его Secret в Vercel и SHA-256 константу в Edge Function; исходный токен никогда не включается в Edge source. Код хранилища: `supabase/functions/bizbox-billing-store/index.ts`; схема: `supabase/bizbox-billing.sql`.

Сервис зависит от доступности Vercel, Supabase и Telegram. При недоступной БД приложение показывает ошибку статуса; ранее выданный действующий резервный код продолжает работать. Размещение использует существующие проекты и их лимиты; новые платные ресурсы не требуются.
